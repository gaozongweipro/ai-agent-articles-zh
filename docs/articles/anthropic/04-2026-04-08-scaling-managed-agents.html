规模化 Managed Agents：把大脑与双手解耦

按照我们的 文档 开始使用 Claude Managed Agents。

Engineering Blog 上的一个持续主题，是如何构建有效智能体，以及如何为长时运行的工作设计 harnesses。贯穿这些工作的一条主线是：harnesses 编码了关于 Claude 独自做不到什么的假设。然而，这些假设需要经常被质疑，因为随着模型进步，它们可能过时。

仅举一例：在先前的工作中，我们发现 Claude Sonnet 4.5 会在感觉自己接近 context 上限时过早收尾——这种行为有时被称为 “context anxiety”。我们通过在 harness 中加入 context resets 来应对。但当我们把同一套 harness 用在 Claude Opus 4.5 上时，发现这种行为已经消失。这些 resets 变成了死重量。

我们预期 harnesses 将继续演化。因此我们构建了 Managed Agents：Claude Platform 上的一项托管服务，通过一小套旨在比任何特定实现（包括我们今天运行的那些）更持久的接口，代表你运行长周期智能体。

构建 Managed Agents 意味着解决计算中的一个老问题：如何为“尚未想到的程序”设计系统。几十年前，操作系统通过把硬件虚拟化为足够通用的抽象——process、file——来解决这个问题，这些抽象足以支撑当时还不存在的程序。抽象比硬件更持久。read() 命令并不关心它访问的是 1970 年代的磁盘组还是现代 SSD。上层抽象保持稳定，底层实现可以自由变化。

Managed Agents 遵循同样的模式。我们将智能体的组成部件虚拟化：session（发生过的一切的只追加日志）、harness（调用 Claude、并把 Claude 的工具调用路由到相关基础设施的循环），以及 sandbox（Claude 可以运行代码和编辑文件的执行环境）。这使得每一部分的实现都可以被替换，而不干扰其他部分。我们对这些接口的形态有明确主张，但对它们背后运行什么并不固执。

不要收养一只宠物（Don’t adopt a pet）

一开始，我们把所有智能体组件放进同一个容器，这意味着 session、agent harness 和 sandbox 共享一个环境。这种方法有好处，包括文件编辑是直接的 syscalls，并且无需设计服务边界。

但把一切耦合进一个容器后，我们碰到了一个老的基础设施问题：我们收养了一只宠物。在 pets-vs-cattle（宠物对牲畜）的类比中，宠物是有名字、需亲手照料、你承受不起失去的个体，而牲畜是可互换的。在我们的情形里，服务器成了那只宠物；如果容器失败，session 就丢失了。如果容器无响应，我们必须把它照料恢复健康。

照料容器意味着调试无响应、卡住的 sessions。我们唯一的窗口是 WebSocket 事件流，但它无法告诉我们失败发生在哪里，这意味着 harness 中的 bug、事件流中的丢包，或容器下线，表现都是一样的。要弄清出了什么问题，工程师必须在容器内打开一个 shell，但因为该容器常常还保存着用户数据，这种方法实际上意味着我们缺乏调试能力。

第二个问题是：harness 假定 Claude 所处理的一切都与它住在同一个容器里。当客户要求我们把 Claude 连接到他们的虚拟私有云时，他们要么必须把网络与我们的对等互联（peer），要么在他们自己的环境中运行我们的 harness。编码进 harness 的一个假设，在我们想把它连接到不同基础设施时，成了问题。

把大脑与双手解耦

我们最终采用的方案，是把我们称为 “大脑”（Claude 及其 harness）的部分，与 “双手”（执行动作的 sandboxes 和工具）以及 “session”（session 事件日志）解耦。每一部分都成为对其他部分几乎不做假设的接口，并且每一部分都可以独立失败或被替换。

Harness 离开容器。 把大脑与双手解耦，意味着 harness 不再住在容器里。它调用容器的方式，与调用任何其他工具相同：execute(name, input) → string。容器变成了牲畜。如果容器死掉，harness 把失败当作工具调用错误捕获，并传回给 Claude。如果 Claude 决定重试，可以用标准配方重新初始化一个新容器：provision({resources})。我们再也不必把失败的容器照料恢复健康。

从 harness 失败中恢复。 Harness 也变成了牲畜。因为 session 日志位于 harness 之外，harness 中没有任何东西需要在崩溃后存活。当一个 harness 失败时，可以用 wake(sessionId) 重启一个新的，用 getSession(id) 取回事件日志，并从最后一个事件恢复。在智能体循环期间，harness 用 emitEvent(id, event) 写入 session，以保持事件的持久记录。

安全边界。 在耦合设计中，Claude 生成的任何不受信任的代码，都与凭证运行在同一个容器中——因此一次 prompt injection 只需说服 Claude 读取自己的环境。一旦攻击者获得这些 tokens，他们就可以生成全新的、不受限制的 sessions，并把工作委托给它们。收窄作用域是一种显而易见的缓解措施，但这编码了一个关于 Claude 用有限 token 做不到什么的假设——而 Claude 正变得越来越聪明。结构性的修复是：确保这些 tokens 永远无法从 Claude 生成的代码所运行的 sandbox 中触及。

我们用两种模式来保证这一点。Auth 可以与资源捆绑在一起，或保存在 sandbox 之外的保险库（vault）中。对于 Git，我们在 sandbox 初始化期间使用每个仓库的 access token 来克隆仓库，并把它接入本地 git remote。Git 的 push 和 pull 可以从 sandbox 内部工作，而智能体从不亲自处理 token。对于定制工具，我们支持 MCP，并把 OAuth tokens 存储在安全保险库中。Claude 通过专用代理调用 MCP 工具；该代理接收一个与 session 关联的 token。代理随后可以从保险库中取出对应凭证，并向外部服务发起调用。Harness 从不被告知任何凭证。

Session 不是 Claude 的 context window

长周期任务常常超出 Claude 的 context window 长度，而应对这一问题的标准方法都涉及关于保留什么的不可逆决策。我们在先前关于 context engineering 的工作中探讨过这些技术。例如，compaction 让 Claude 保存其 context window 的摘要，memory tool 让 Claude 把 context 写入文件，从而支持跨 session 学习。这可以与 context trimming 配对，后者有选择地移除旧的工具结果或 thinking blocks 等 tokens。

但对保留或丢弃 context 做出不可逆决策，可能导致失败。很难知道未来的轮次会需要哪些 tokens。如果消息被 compaction 步骤转换，harness 会把被压缩的消息从 Claude 的 context window 中移除，而这些消息只有在被存储的情况下才可恢复。先前的工作探讨过通过把 context 存储为生活在 context window 之外的对象来解决这个问题。例如，context 可以是 REPL 中的一个对象，LLM 通过编写代码来过滤或切片它，从而以编程方式访问。

在 Managed Agents 中，session 提供了同样的好处，作为生活在 Claude 的 context window 之外的 context 对象。但 context 不是存储在 sandbox 或 REPL 中，而是持久地存储在 session 日志里。接口 getEvents() 允许大脑通过选择事件流的位置切片来询问 context。该接口可以灵活使用，使大脑可以从上次停止阅读的地方继续、在特定时刻之前回退几个事件以查看前因，或在特定动作之前重读 context。

任何取出的事件也可以在传入 Claude 的 context window 之前，在 harness 中被转换。这些转换可以是 harness 所编码的任何内容，包括为了实现高 prompt cache 命中率而做的 context 组织，以及 context engineering。我们把可恢复的 context 存储（在 session 中）与任意的 context 管理（在 harness 中）分开，因为我们无法预测未来模型将需要怎样具体的 context engineering。这些接口把 context 管理推向 harness，只保证 session 是持久的、并且可供询问。

许多大脑，许多双手

许多大脑。 把大脑与双手解耦，解决了我们最早的客户抱怨之一。当团队希望 Claude 针对他们自己 VPC 中的资源工作时，唯一的路径是把他们的网络与我们的对等互联，因为持有 harness 的容器假定每项资源都在它旁边。一旦 harness 不再位于容器中，这一假设就消失了。同样的改变还有性能收益。当我们最初把大脑放进容器时，意味着有多少大脑就需要多少容器。对每个大脑而言，在该容器被配置完成之前，无法进行任何推理；每个 session 都要预先支付完整的容器启动成本。每一个 session，即使是那些永远不会触及 sandbox 的，都必须克隆仓库、启动进程、从我们的服务器获取待处理事件。

这段空转时间表现为 time-to-first-token（TTFT），衡量的是一个 session 在接受工作与产出第一个回复 token 之间等待了多久。TTFT 是用户最能敏锐感受到的延迟。

把大脑与双手解耦，意味着容器仅在需要时由大脑通过工具调用（execute(name, input) → string）来配置。因此，一个并不立刻需要容器的 session 不必等待容器。推理可以在编排层从 session 日志拉取待处理事件后立即开始。使用这一架构，我们的 p50 TTFT 下降了大约 60%，p95 下降超过 90%。扩展到许多大脑，只意味着启动许多无状态的 harnesses，并仅在需要时把它们连接到双手。

许多双手。 我们还希望能够把每个大脑连接到许多双手。在实践中，这意味着 Claude 必须对许多执行环境进行推理，并决定把工作送到哪里——这比在单个 shell 中操作更难的认知任务。我们一开始把大脑放在单个容器中，是因为早期模型还没有这种能力。随着智能扩展，单个容器反而成了限制：当该容器失败时，我们会丢失大脑所伸向的每一双手的状态。

把大脑与双手解耦，使每一双手都成为一个工具，execute(name, input) → string：输入一个名称和输入，返回一个字符串。该接口支持任何定制工具、任何 MCP server，以及我们自己的工具。Harness 并不知道 sandbox 是一个容器、一部手机，还是一个宝可梦模拟器。而且因为没有一双手与任何一个大脑耦合，大脑可以把双手传递给彼此。

结论

我们所面临的挑战是一个老问题：如何为“尚未想到的程序”设计系统。操作系统之所以能持续数十年，是因为它们把硬件虚拟化为足够通用、足以支撑当时还不存在的程序的抽象。通过 Managed Agents，我们的目标是设计一个能容纳未来围绕 Claude 的 harnesses、sandboxes 或其他组件的系统。

Managed Agents 在同样的精神下是一个 meta-harness，对 Claude 未来将需要的特定 harness 并不固执。相反，它是一个带有通用接口、允许许多不同 harnesses 的系统。例如，Claude Code 是我们在各种任务中广泛使用的优秀 harness。我们也已经表明，任务特定的智能体 harnesses 在狭窄领域中表现出色。Managed Agents 可以容纳其中任何一种，并随着时间与 Claude 的智能相匹配。

Meta-harness 设计意味着对围绕 Claude 的接口有明确主张：我们预期 Claude 将需要操纵状态（session）和执行计算（sandbox）的能力。我们也预期 Claude 将需要扩展到许多大脑和许多双手的能力。我们设计这些接口，使它们可以在长周期上可靠且安全地运行。但我们对 Claude 将需要的大脑或双手的数量或位置不做假设。
