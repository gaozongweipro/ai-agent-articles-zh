# 我们如何构建多智能体研究系统

Claude 现在拥有 [Research 能力](https://www.anthropic.com/news/research)，使其可以跨网页、Google Workspace 以及任何集成进行搜索，以完成复杂任务。

这一多智能体系统从原型到生产的旅程，教会了我们关于系统架构、工具设计和 prompt engineering 的关键教训。一个多智能体系统由多个智能体（在循环中自主使用工具的 LLM）协同工作组成。我们的 Research 功能涉及一个智能体根据用户查询规划研究过程，然后使用工具创建并行智能体同时搜索信息。带有多个智能体的系统在智能体协调、评估和可靠性方面引入了新的挑战。

本文将拆解对我们有效的原则——希望你在构建自己的多智能体系统时会发现它们有用。

## 多智能体系统的好处

研究工作涉及开放式问题，很难预先预测所需步骤。你无法为探索复杂主题硬编码一条固定路径，因为该过程本质上是动态的、路径依赖的。当人们做研究时，他们往往会根据发现持续更新方法，跟随调查过程中出现的线索。

这种不可预测性使 AI 智能体特别适合研究任务。研究需要在调查展开时转向或探索切线连接的灵活性。模型必须自主运作许多轮，根据中间发现决定追求哪些方向。线性的一次性流水线无法处理这些任务。

搜索的本质是压缩：从庞大语料中提炼洞见。Subagents 通过在各自的 context windows 中并行运作来促进压缩，同时探索问题的不同方面，然后再把最重要的 tokens 浓缩给主导研究智能体。每个 subagent 也提供关注点分离——不同的工具、prompts 和探索轨迹——这减少了路径依赖，并实现彻底、独立的调查。

一旦智能达到某个阈值，多智能体系统就成为扩展表现的关键方式。例如，尽管在过去 10 万年里单个变得更聪明，但人类社会在信息时代变得*指数级*更有能力，是因为我们的*集体*智能和协调能力。即使是一般智能的智能体，作为个体运作时也面临限制；成组的智能体可以完成远多得多的事情。

我们的内部评估显示，多智能体研究系统尤其擅长广度优先的查询，这类查询涉及同时追求多个独立方向。我们发现，以 Claude Opus 4 作为主导智能体、以 Claude Sonnet 4 作为 subagents 的多智能体系统，在我们的内部研究评估上比单智能体 Claude Opus 4 高出 90.2%。例如，当被要求识别信息技术行业标普 500 公司的全部董事会成员时，多智能体系统通过把这件事分解为交给 subagents 的任务找到了正确答案，而单智能体系统则以缓慢的顺序搜索未能找到答案。

多智能体系统之所以有效，主要是因为它们帮助花费足够的 tokens 来解决问题。在我们的分析中，三个因素解释了 [BrowseComp](https://openai.com/index/browsecomp/) 评估（测试浏览智能体定位难以找到的信息的能力）中 95% 的表现方差。我们发现，仅 token 用量本身就解释了 80% 的方差，工具调用次数和模型选择是另外两个解释因素。这一发现验证了我们的架构：把工作分布到带有独立 context windows 的智能体上，以增加并行推理的容量。最新的 Claude 模型对 token 使用起着很大的效率倍增作用，因为升级到 Claude Sonnet 4 带来的表现提升，大于把 Claude Sonnet 3.7 的 token 预算加倍。多智能体架构有效地为超出单智能体限制的任务扩展 token 用量。

也有下行方面：在实践中，这些架构会迅速消耗 tokens。在我们的数据中，智能体通常比聊天交互多用大约 4 倍的 tokens，而多智能体系统比聊天多用大约 15 倍的 tokens。为了经济上可行，多智能体系统需要任务价值高到足以支付提升后的表现。此外，某些要求所有智能体共享同一 context、或智能体之间有许多依赖的领域，目前并不适合多智能体系统。例如，大多数编程任务中真正可并行化的任务比研究少，而且 LLM 智能体还不太擅长实时协调和委托给其他智能体。我们发现，多智能体系统擅长有价值的、涉及大量并行化、信息超出单个 context window、以及需要与众多复杂工具交互的任务。

## Research 的架构概述

我们的 Research 系统使用带有编排器-工作者（orchestrator-worker）模式的多智能体架构：一个主导智能体协调过程，同时把工作委托给并行运作的专门 subagents。

（原文配图：多智能体架构运作示意：用户查询流经一个创建专门 subagents 以并行搜索不同方面的主导智能体。）

多智能体架构的运作：用户查询流经一个主导智能体，该智能体创建专门的 subagents 以并行搜索不同方面。

当用户提交查询时，主导智能体分析它，制定策略，并派生 subagents 同时探索不同方面。如上图所示，subagents 充当智能过滤器，通过迭代使用搜索工具收集信息——在这个例子中是关于 2025 年 AI 智能体公司的信息——然后把公司列表返回给主导智能体，以便它汇编最终答案。

使用 Retrieval Augmented Generation（RAG）的传统方法采用静态检索。也就是说，它们获取与输入查询最相似的一组块，并用这些块生成响应。相比之下，我们的架构使用多步骤搜索，动态地找到相关信息，适应新发现，并分析结果以形成高质量答案。

（原文配图：展示多智能体 Research 系统完整工作流的过程图。）

过程图展示了我们多智能体 Research 系统的完整工作流。当用户提交查询时，系统创建一个 LeadResearcher 智能体，进入迭代研究过程。LeadResearcher 首先思考方法，并把计划保存到 Memory 以持久化 context，因为如果 context window 超过 200,000 tokens 就会被截断，而保留计划很重要。然后它创建带有特定研究任务的专门 Subagents（这里展示了两个，但可以是任意数量）。每个 Subagent 独立执行网页搜索，使用 [interleaved thinking](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking#interleaved-thinking) 评估工具结果，并把发现返回给 LeadResearcher。LeadResearcher 综合这些结果，并决定是否需要更多研究——如果需要，它可以创建额外的 subagents 或精炼其策略。一旦收集到足够信息，系统退出研究循环，并把全部发现传给 CitationAgent，后者处理文档和研究报告，以识别引用的具体位置。这确保所有主张都被正确归因到其来源。最终的研究结果连同引用一起返回给用户。

## 面向研究智能体的 Prompt engineering 与评估

多智能体系统与单智能体系统有关键差异，包括协调复杂度的快速增长。早期智能体会犯这样的错误：为简单查询派生 50 个 subagents、没完没了地在网上搜寻不存在的来源，以及用过多更新让彼此分心。因为每个智能体都由 prompt 引导，prompt engineering 是我们改进这些行为的主要杠杆。下面是我们为给智能体做 prompting 所学到的一些原则：

1. **像你的智能体一样思考。** 要迭代 prompts，你必须理解它们的效果。为帮助我们做到这一点，我们使用 [Console](https://console.anthropic.com/)、以系统中完全相同的 prompts 和工具构建模拟，然后逐步观察智能体工作。这立即揭示了失败模式：智能体在已有足够结果时仍继续、使用过于冗长的搜索查询，或选择不正确的工具。有效的 prompting 依赖于对智能体建立准确的心智模型，这可以使最有影响力的改动变得显而易见。
2. **教编排器如何委托。** 在我们的系统中，主导智能体把查询分解为子任务，并把它们描述给 subagents。每个 subagent 需要一个目标、一种输出格式、关于使用哪些工具和来源的指导，以及清晰的任务边界。如果没有详细的任务描述，智能体会重复工作、留下空白，或未能找到必要信息。一开始我们允许主导智能体给出简单、简短的指令，例如 “研究半导体短缺”，但发现这些指令往往足够模糊，以至于 subagents 误解任务，或执行与其他智能体完全相同的搜索。例如，一个 subagent 探索了 2021 年汽车芯片危机，而另外两个重复调查当前 2025 年的供应链，没有有效的劳动分工。
3. **按查询复杂度扩展投入。** 智能体难以判断不同任务的适当投入，因此我们在 prompts 中嵌入了扩展规则。简单的事实查找只需要 1 个智能体、3–10 次工具调用；直接比较可能需要 2–4 个 subagents，每个 10–15 次调用；复杂研究可能使用超过 10 个 subagents，并有清晰划分的职责。这些显式指南帮助主导智能体高效分配资源，并防止在简单查询上过度投入，而这是我们早期版本中的常见失败模式。
4. **工具设计与选择至关重要。** 智能体-工具接口与人机接口同样关键。使用正确的工具是高效的——常常还是严格必要的。例如，一个在网上搜索只存在于 Slack 中的 context 的智能体从一开始就注定失败。随着 [MCP servers](https://modelcontextprotocol.io/introduction) 让模型能够访问外部工具，这一问题会叠加，因为智能体会遇到从未见过的、描述质量千差万别的工具。我们给智能体提供了显式启发式：例如，先检查所有可用工具，使工具使用与用户意图匹配，用网页搜索做广泛的外部探索，或优先使用专门工具而不是通用工具。糟糕的工具描述可能把智能体完全送上错误道路，因此每个工具都需要独特的用途和清晰的描述。
5. **让智能体改进自己。** 我们发现 Claude 4 模型可以是出色的 prompt engineers。当被给予一份 prompt 和一种失败模式时，它们能够诊断智能体为何失败并建议改进。我们甚至创建了一个工具测试智能体——当被给予一个有缺陷的 MCP 工具时，它会尝试使用该工具，然后重写工具描述以避免失败。通过数十次测试该工具，这个智能体发现了关键细微差别和 bug。这一改进工具人体工学的过程，使未来使用新描述的智能体任务完成时间减少了 40%，因为它们能够避免大多数错误。
6. **先广后窄。** 搜索策略应当镜像专家人类研究：先探索全貌，再深入细节。智能体常常默认使用过长、过具体的查询，返回很少结果。我们通过提示智能体先从短而宽的查询开始、评估有什么可用、然后逐步收窄焦点，来对抗这一倾向。
7. **引导思考过程。** [Extended thinking 模式](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking) 会让 Claude 在可见的思考过程中输出额外 tokens，可以用作可控的草稿本。主导智能体用思考来规划其方法，评估哪些工具适合该任务，确定查询复杂度和 subagent 数量，并定义每个 subagent 的角色。我们的测试显示，extended thinking 改进了指令遵循、推理和效率。Subagents 也会先做规划，然后在工具结果之后使用 [interleaved thinking](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking#interleaved-thinking) 来评估质量、识别缺口并精炼下一次查询。这使 subagents 在适应任何任务时更有效。
8. **并行工具调用改变速度和表现。** 复杂研究任务自然涉及探索许多来源。我们早期的智能体执行顺序搜索，慢得令人痛苦。为了速度，我们引入了两种并行化：(1) 主导智能体并行而不是串行启动 3–5 个 subagents；(2) subagents 并行使用 3+ 个工具。这些改动使复杂查询的研究时间最多缩短 90%，使 Research 能在几分钟而不是几小时内完成更多工作，同时覆盖比其他系统更多的信息。

我们的 prompting 策略聚焦于灌输良好的启发式，而不是僵硬的规则。我们研究了熟练的人类如何处理研究任务，并把这些策略编码进 prompts——例如把困难问题分解成更小的任务、仔细评估来源质量、根据新信息调整搜索方法，以及识别何时聚焦深度（详细调查一个主题）与广度（并行探索许多主题）。我们还通过设置显式护栏来主动缓解意外副作用，以防止智能体失控盘旋。最后，我们聚焦于带有可观测性和测试用例的快速迭代循环。

## 对智能体的有效评估

好的评估对于构建可靠的 AI 应用至关重要，智能体也不例外。然而，评估多智能体系统带来独特挑战。传统评估常常假定 AI 每次遵循相同步骤：给定输入 X，系统应当沿路径 Y 产生输出 Z。但多智能体系统不是这样工作的。即使起点相同，智能体也可能走完全不同的有效路径到达目标。一个智能体可能搜索三个来源，而另一个搜索十个，或者它们可能使用不同工具找到相同答案。因为我们并不总是知道正确步骤是什么，通常不能只检查智能体是否遵循了我们预先规定的“正确”步骤。相反，我们需要灵活的评估方法，判断智能体是否达成了正确结果，同时也遵循了合理过程。

**立刻用小样本开始评估。** 在智能体开发早期，改动往往有戏剧性影响，因为有大量容易摘到的果实。一次 prompt 微调可能把成功率从 30% 提升到 80%。效果如此之大，只需几个测试用例就能发现变化。我们从大约 20 个代表真实使用模式的查询开始。测试这些查询常常让我们清楚地看到改动的影响。我们常听到 AI 开发团队推迟创建评估，因为他们相信只有带有数百个测试用例的大型评估才有用。然而，最好立刻用几个例子开始小规模测试，而不是等到能构建更彻底的评估再开始。

**做好的 LLM-as-judge 评估可以扩展。** 研究输出很难用程序评估，因为它们是自由形式的文本，很少有单一正确答案。LLM 天然适合为输出打分。我们使用一个 LLM 评判者，对照量规中的标准评估每个输出：事实准确性（主张是否与来源相符？）、引用准确性（被引用的来源是否与主张相符？）、完整性（是否覆盖了所有被要求的方面？）、来源质量（是否优先使用一手来源而不是质量较低的二手来源？），以及工具效率（是否以合理次数使用了正确工具？）。我们尝试过用多个评判者评估每个组成部分，但发现一次带有单个 prompt 的 LLM 调用，输出 0.0–1.0 的分数和通过-失败等级，最为一致，也最与人类判断对齐。当评估测试用例*确实*有明确答案，并且我们可以用 LLM 评判者简单地检查答案是否正确时（例如，它是否准确列出了研发预算最大的前 3 家制药公司？），这种方法尤其有效。把 LLM 用作评判者使我们能够规模化地评估数百份输出。

**人工评估能抓住自动化错过的东西。** 测试智能体的人会发现评估错过的边界情况。这包括对异常查询的幻觉答案、系统故障，或微妙的来源选择偏见。在我们的情形中，人工测试者注意到，我们早期的智能体一直选择 SEO 优化的内容农场，而不是学术 PDF 或个人博客等权威但排名不那么高的来源。在 prompts 中加入来源质量启发式帮助解决了这一问题。即使在自动化评估的世界里，手动测试仍然必不可少。

多智能体系统有涌现行为，这些行为在没有特定编程的情况下出现。例如，对主导智能体的小改动可能不可预测地改变 subagents 的行为。成功需要理解交互模式，而不仅仅是单个智能体行为。因此，这些智能体的最佳 prompts 不仅仅是严格指令，而是定义劳动分工、问题解决方法和投入预算的协作框架。把这一点做对，依赖于仔细的 prompting 和工具设计、扎实的启发式、可观测性，以及紧密的反馈循环。参见我们 Cookbook 中的[开源 prompts](https://platform.claude.com/cookbook/patterns-agents-basic-workflows)，以了解来自我们系统的示例 prompts。

## 生产可靠性与工程挑战

在传统软件中，一个 bug 可能破坏某项功能、降低表现或造成停机。在智能体系统中，微小改动会级联成巨大的行为变化，这使得为必须在长时运行过程中维护状态的复杂智能体编写代码变得极其困难。

**智能体是有状态的，错误会累积。** 智能体可以长时间运行，跨许多工具调用维护状态。这意味着我们需要持久地执行代码，并沿途处理错误。如果没有有效缓解措施，轻微的系统故障对智能体可能是灾难性的。当错误发生时，我们不能只是从头重新开始：重启代价昂贵，也会让用户沮丧。相反，我们构建了可以从错误发生时智能体所在位置恢复的系统。我们也利用模型的智能来优雅地处理问题：例如，让智能体知道某个工具正在失败并让它适应，效果出人意料地好。我们把建立在 Claude 之上的 AI 智能体的适应能力，与重试逻辑和定期检查点等确定性保障结合起来。

**调试受益于新方法。** 智能体做出动态决策，即使 prompts 相同，不同运行之间也是非确定性的。这使调试更难。例如，用户会报告智能体“找不到显而易见的信息”，但我们看不到原因。是智能体使用了糟糕的搜索查询？选择了差的来源？还是遇到了工具故障？加入完整的生产 tracing 让我们能诊断智能体为何失败，并系统地修复问题。除了标准可观测性之外，我们还监控智能体决策模式和交互结构——同时不监控单个对话的内容，以维护用户隐私。这种高层可观测性帮助我们诊断根本原因、发现意外行为，并修复常见失败。

**部署需要仔细协调。** 智能体系统是高度有状态的 prompts、工具和几乎持续运行的执行逻辑之网。这意味着无论何时部署更新，智能体都可能处于其过程中的任何位置。因此我们需要防止善意的代码改动破坏正在运行的智能体。我们不能同时把每个智能体更新到新版本。相反，我们使用 [rainbow deployments](https://brandon.dimcheff.com/2018/02/rainbow-deploys-with-kubernetes/) 来避免干扰正在运行的智能体，通过在同时运行旧版本和新版本的同时，逐渐把流量从旧版本转移到新版本。

**同步执行会造成瓶颈。** 目前，我们的主导智能体同步执行 subagents，等待每一组 subagents 完成后再继续。这简化了协调，但在智能体之间的信息流中造成瓶颈。例如，主导智能体无法引导 subagents，subagents 无法相互协调，整个系统可能在等待单个 subagent 完成搜索时被阻塞。异步执行将启用额外的并行：智能体同时工作，并在需要时创建新的 subagents。但这种异步性在结果协调、状态一致性以及跨 subagents 的错误传播方面增加了挑战。随着模型能够处理更长、更复杂的研究任务，我们预期表现收益将证明这种复杂度是值得的。

## 结论

在构建 AI 智能体时，最后一公里常常成为旅程的大部分。在开发者机器上能工作的代码库，需要显著的工程才能成为可靠的生产系统。智能体系统中错误的复合性质意味着，对传统软件而言较小的问题可能完全使智能体脱轨。一步失败可能导致智能体探索完全不同的轨迹，带来不可预测的结果。出于本文描述的所有原因，原型与生产之间的鸿沟往往比预期更宽。

尽管有这些挑战，多智能体系统已被证明对开放式研究任务有价值。用户表示，Claude 帮助他们发现了未曾考虑的商业机会、导航复杂的医疗选项、解决棘手的技术 bug，并通过揭示他们独自不会发现的研究联系，节省了多达数天的工作。多智能体研究系统可以通过仔细的工程、全面的测试、注重细节的 prompt 和工具设计、稳健的运维实践，以及在研究、产品和工程团队之间对当前智能体能力有深刻理解的紧密协作，在规模上可靠运作。我们已经看到这些系统正在改变人们解决复杂问题的方式。

## 附录

下面是关于多智能体系统的一些额外零散提示。

**对在多轮中改变状态的智能体做终态评估。** 评估在多轮对话中修改持久状态的智能体，带来独特挑战。与只读研究任务不同，每一个动作都可能改变后续步骤的环境，造成传统评估方法难以处理的依赖。我们发现，聚焦于终态评估而不是逐轮分析是成功的。与其判断智能体是否遵循了特定过程，不如评估它是否达成了正确的最终状态。这种方法承认智能体可能找到通往同一目标的替代路径，同时仍确保它们交付预期结果。对于复杂工作流，把评估拆成离散检查点，在这些点上特定的状态变化应当已经发生，而不是试图验证每一个中间步骤。

**长周期对话管理。** 生产智能体常常参与跨越数百轮的对话，需要仔细的 context 管理策略。随着对话延长，标准 context windows 变得不足，需要智能压缩和记忆机制。我们实现了一些模式：智能体总结已完成的工作阶段，并在进入新任务之前把必要信息存储到外部记忆中。当接近 context 上限时，智能体可以派生带有干净 context 的全新 subagents，同时通过仔细的交接保持连续性。此外，它们可以从记忆中检索已存储的 context（例如研究计划），而不是在达到 context 上限时丢失先前工作。这种分布式方法防止 context 溢出，同时在延长交互中保持对话连贯性。

**把 Subagent 输出写到文件系统，以尽量减少“传话游戏”。** 对于某些类型的结果，直接的 subagent 输出可以绕过主协调器，同时提高保真度和表现。与其要求 subagents 通过主导智能体传达一切，不如实现产物系统，让专门智能体可以创建独立持久化的输出。Subagents 调用工具把工作存储在外部系统中，然后把轻量引用传回协调器。这防止了多阶段处理中的信息丢失，并减少了通过对话历史复制大型输出的 token 开销。这一模式对结构化输出特别有效，例如代码、报告或数据可视化，在这些情况下 subagent 的专门 prompt 比经过通用协调器过滤能产生更好的结果。
