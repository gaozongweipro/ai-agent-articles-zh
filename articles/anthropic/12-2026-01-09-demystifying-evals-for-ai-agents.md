# 揭开 AI 智能体评估的神秘面纱

## 引言

好的评估帮助团队更有信心地交付 AI 智能体。没有它们，很容易陷入被动循环——只在生产中发现问题，而在那里修复一次失败又会造成其他失败。Evals 使问题和行为变化在影响用户之前就变得可见，其价值会在智能体的生命周期中复合增长。

正如我们在 [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) 中所描述的，智能体跨越许多轮运作：调用工具、修改状态，并根据中间结果适应。正是这些使 AI 智能体有用的能力——自主性、智能和灵活性——也使它们更难评估。

通过我们的内部工作，以及与处于智能体开发前沿的客户合作，我们学会了如何为智能体设计更严格、更有用的 evals。下面是在真实部署中跨一系列智能体架构和用例行之有效的做法。

## 一次评估的结构

一次 **evaluation**（“eval”）是对 AI 系统的一次测试：给 AI 一个输入，然后对其输出应用评分逻辑以衡量成功。在本文中，我们聚焦于可以在开发期间、无需真实用户即可运行的 **automated evals（自动化评估）**。

**单轮评估（Single-turn evaluations）** 很直接：一个 prompt、一个响应，以及评分逻辑。对于较早的 LLM，单轮、非智能体式的 evals 是主要评估方法。随着 AI 能力进步，**多轮评估（multi-turn evaluations）** 变得越来越常见。

（原文配图：在简单 eval 中，智能体处理一个 prompt，评分器检查输出是否符合预期。在更复杂的多轮 eval 中，编程智能体收到工具、一项任务（在这个例子中是构建 MCP server）和环境，执行一个 “agent loop”（工具调用和推理），并用实现更新环境。然后评分使用单元测试来验证可用的 MCP server。）

**智能体评估（Agent evaluations）** 甚至更复杂。智能体跨许多轮使用工具，修改环境中的状态并边走边适应——这意味着错误可以传播并累积。前沿模型也可以找到超越静态 evals 限制的创造性方案。例如，Opus 4.5 通过[发现](https://www.anthropic.com/news/claude-opus-4-5)政策中的一个漏洞，解决了一个关于预订航班的 [𝜏2-bench](https://github.com/sierra-research/tau2-bench) 问题。它按书面评估“失败”了，但实际上为用户想出了更好的方案。

在构建智能体评估时，我们使用以下定义：

- 一个 **task**（又称 **problem** 或 **test case**）是一次带有定义输入和成功标准的单个测试。
- 对一项任务的每一次尝试是一次 **trial**。因为模型输出在不同运行之间会变化，我们运行多次 trials 以产生更一致的结果。
- 一个 **grader** 是为智能体表现的某个方面打分的逻辑。一项任务可以有多个 graders，每个包含多个断言（有时称为 **checks**）。
- 一份 **transcript**（也称为 **trace** 或 **trajectory**）是一次 trial 的完整记录，包括输出、工具调用、推理、中间结果以及任何其他交互。对于 Anthropic API，这是一次 eval 运行结束时的完整 messages 数组——包含评估期间对 API 的全部调用以及返回的全部响应。
- **outcome** 是 trial 结束时环境中的最终状态。一个航班预订智能体可能在 transcript 结尾说 “Your flight has been booked”，但 outcome 是环境的 SQL 数据库中是否存在一份预订。
- 一个 **evaluation harness** 是端到端运行 evals 的基础设施。它提供指令和工具，并发运行任务，记录全部步骤，为输出打分，并汇总结果。
- 一个 **agent harness**（或 **scaffold**）是使模型能作为智能体行动的系统：它处理输入、编排工具调用并返回结果。当我们评估“一个智能体”时，我们评估的是 harness *和* 模型一起工作。例如，[Claude Code](https://claude.com/product/claude-code) 是一个灵活的 agent harness，我们通过 [Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) 使用其核心原语构建了我们的[长时运行智能体 harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)。
- 一个 **evaluation suite** 是一套旨在衡量特定能力或行为的任务集合。一个 suite 中的任务通常共享一个宽泛目标。例如，一个客服 eval suite 可能测试退款、取消和升级。

## 为什么要构建评估？

当团队刚开始构建智能体时，他们可以通过手动测试、[dogfooding](https://en.wikipedia.org/wiki/Eating_your_own_dog_food) 和直觉的组合，出人意料地走得很远。更严格的评估甚至可能看起来像是拖慢交付的开销。但在早期原型阶段之后，一旦智能体进入生产并开始扩展，没有 evals 地构建就会开始崩溃。

崩溃点常常出现在用户报告智能体在改动后感觉更差，而团队在“盲目飞行”、除了猜测和检查之外没有办法验证的时候。没有 evals，调试是被动的：等待投诉、手动复现、修复 bug，并希望没有其他东西退化。团队无法区分真实退化与噪声，无法在交付前自动对照数百个场景测试改动，也无法衡量改进。

我们多次看到这一进程展开。例如，Claude Code 一开始基于 Anthropic 员工和外部用户的反馈快速迭代。后来，我们加入了 evals——先针对简洁性和文件编辑等狭窄领域，然后针对过度工程等更复杂行为。这些 evals 帮助识别问题、引导改进，并聚焦研究与产品的协作。与生产监控、A/B 测试、用户研究等相结合，evals 提供信号，以在 Claude Code 扩展时持续改进它。

在智能体生命周期的任何阶段撰写 evals 都是有用的。早期，evals 迫使产品团队明确成功对智能体意味着什么；后来，它们帮助维持一致的质量标准。

[Descript](https://www.descript.com/) 的智能体帮助用户编辑视频，因此他们围绕成功编辑工作流的三个维度构建 evals：不要弄坏东西、做我要求的事、并且做好。他们从手动评分演进到由产品团队定义标准、并定期进行人工校准的 LLM graders，现在定期运行两套独立的 suites：一套用于质量基准，一套用于退化测试。[Bolt](https://bolt.new/) AI 团队在已经拥有广泛使用的智能体之后才开始构建 evals。在 3 个月内，他们构建了一套评估系统：运行他们的智能体，用静态分析为输出打分，使用浏览器智能体测试应用，并使用 LLM judges 评估指令遵循等行为。

有些团队在开发开始时就创建 evals；另一些在达到规模、evals 成为改进智能体的瓶颈时才加入它们。Evals 在智能体开发开始时尤其有用，可以显式编码期望行为。两位工程师阅读同一份初始规格，可能对 AI 应如何处理边界情况得出不同解释。一套 eval suite 解决这种歧义。无论何时创建，evals 都有助于加速开发。

Evals 也塑造你能多快采用新模型。当更强大的模型出现时，没有 evals 的团队面临数周测试，而有 evals 的竞争对手可以迅速确定模型的优势、调优 prompts，并在几天内升级。

一旦 evals 存在，你就免费获得基线和退化测试：延迟、token 用量、每项任务成本和错误率可以在静态任务库上被跟踪。Evals 也可以成为产品和研究团队之间带宽最高的沟通渠道，定义研究人员可以对照优化的指标。显然，evals 除了跟踪退化和改进之外还有广泛好处。其复合价值很容易被错过，因为成本在前期可见，而收益在稍后累积。

## 如何评估 AI 智能体

我们看到今天有几种在规模上部署的常见智能体类型，包括编程智能体、研究智能体、计算机使用智能体和对话智能体。每种类型可能部署在各种各样的行业中，但它们可以用类似技术来评估。你不需要从头发明一次评估。下面各节描述针对几种智能体类型已被证明的技术。把这些方法作为基础，然后扩展到你的领域。

### 面向智能体的评分器类型

智能体评估通常组合三种评分器：基于代码的、基于模型的，以及人工的。每个评分器评估 transcript 或 outcome 的某一部分。有效评估设计的一个必要组成部分，是为工作选择正确的评分器。

## 基于代码的评分器（Code-based graders）

| **方法** | **优点** | **弱点** |
| --- | --- | --- |
| • 字符串匹配检查（精确、regex、模糊等）<br>• 二元测试（fail-to-pass、pass-to-pass）<br>• 静态分析（lint、类型、安全）<br>• Outcome 验证<br>• 工具调用验证（使用的工具、参数）<br>• Transcript 分析（所用轮次、token 用量） | • 快速<br>• 便宜<br>• 客观<br>• 可复现<br>• 易于调试<br>• 验证特定条件 | • 对不完全匹配期望模式的有效变体很脆弱<br>• 缺乏细微差别<br>• 对评估某些更主观的任务有限 |

## 基于模型的评分器（Model-based graders）

| **方法** | **优点** | **弱点** |
| --- | --- | --- |
| • 基于量规的评分<br>• 自然语言断言<br>• 成对比较<br>• 基于参考的评估<br>• 多评判者共识 | • 灵活<br>• 可扩展<br>• 捕捉细微差别<br>• 处理开放式任务<br>• 处理自由形式输出 | • 非确定性<br>• 比代码更昂贵<br>• 需要与人工评分器校准以获得准确性 |

## 人工评分器（Human graders）

| **方法** | **优点** | **弱点** |
| --- | --- | --- |
| • 主题专家（SME）审阅<br>• 众包判断<br>• 抽查采样<br>• A/B 测试<br>• 标注者间一致性 | • 黄金标准质量<br>• 与专家用户判断匹配<br>• 用于校准基于模型的评分器 | • 昂贵<br>• 缓慢<br>• 常常需要大规模访问人类专家 |

对每项任务，评分可以是加权的（组合评分器分数必须达到阈值）、二元的（所有评分器必须通过），或混合的。

### 能力评估 vs. 退化评估

**能力或“质量”评估（Capability or “quality” evals）** 问的是：“这个智能体能做好什么？”它们应当从低通过率开始，瞄准智能体感到困难的任务，并给团队一座可以攀登的山。

**退化评估（Regression evals）** 问的是：“智能体是否仍然处理它过去能处理的全部任务？”并且应当有接近 100% 的通过率。它们防止后退，因为分数下降表明有东西坏了、需要改进。当团队在能力评估上爬山时，同时运行退化评估也很重要，以确保改动不会在其他地方造成问题。

在智能体上线并被优化之后，通过率高的能力评估可以“毕业”成为持续运行以捕捉任何漂移的退化 suite。曾经衡量“我们到底能不能做这件事？”的任务，随后衡量“我们是否仍然能可靠地做这件事？”

### 评估编程智能体

**编程智能体（Coding agents）** 编写、测试和调试代码，像人类开发者一样导航代码库并运行命令。面向现代编程智能体的有效 evals 通常依赖规格良好的任务、稳定的测试环境，以及对生成代码的彻底测试。

确定性评分器对编程智能体是自然的，因为软件通常易于评估：代码能否运行、测试能否通过？两个广泛使用的编程智能体基准，[SWE-bench Verified](https://www.swebench.com/SWE-bench/) 和 [Terminal-Bench](https://www.tbench.ai/)，遵循这一方法。SWE-bench Verified 给智能体来自流行 Python 仓库的 GitHub issues，并通过运行测试套件为方案打分；只有在修复失败测试且不破坏现有测试的情况下，方案才通过。LLM 在这一评估上仅一年就从 40% 进步到 >80%。Terminal-Bench 走不同路线：它测试端到端技术任务，例如从源码构建 Linux 内核或训练一个 ML 模型。

一旦你有一套用于验证编程任务关键 *outcomes* 的通过或失败测试，为 transcript 打分也常常有用。例如，基于启发式的代码质量规则可以根据不仅仅是通过测试来评估生成的代码，而带有清晰量规的基于模型的评分器可以评估智能体如何调用工具或与用户交互等行为。

**示例：编程智能体的理论评估**

考虑一项编程任务，智能体必须修复一个认证绕过漏洞。如下面说明性的 YAML 文件所示，人们可以使用评分器和指标来评估该智能体。

```plaintext
task:
  id: "fix-auth-bypass_1"
  desc: "Fix authentication bypass when password field is empty and ..."
  graders:
    - type: deterministic_tests
      required: [test_empty_pw_rejected.py, test_null_pw_rejected.py]
    - type: llm_rubric
      rubric: prompts/code_quality.md
    - type: static_analysis
      commands: [ruff, mypy, bandit]
    - type: state_check
      expect:
        security_logs: {event_type: "auth_blocked"}
    - type: tool_calls
      required:
        - {tool: read_file, params: {path: "src/auth/*"}}
        - {tool: edit_file}
        - {tool: run_tests}
  tracked_metrics:
    - type: transcript
      metrics:
        - n_turns
        - n_toolcalls
        - n_total_tokens
    - type: latency
      metrics:
        - time_to_first_token
        - output_tokens_per_sec
        - time_to_last_token
```

注意，这个例子为说明目的展示了全部可用评分器的范围。在实践中，编程评估通常依赖单元测试做正确性验证，以及一份 LLM 量规来评估整体代码质量，只有在需要时才加入额外评分器和指标。

### 评估对话智能体

**对话智能体（Conversational agents）** 在支持、销售或辅导等领域与用户交互。与传统聊天机器人不同，它们维护状态、使用工具，并在对话中途采取行动。虽然编程和研究智能体也可以涉及与用户的许多轮交互，对话智能体提出了一个独特挑战：交互本身的质量是你在评估的内容的一部分。面向对话智能体的有效 evals 通常依赖可验证的终态 outcomes，以及同时捕捉任务完成和交互质量的量规。与大多数其他 evals 不同，它们常常需要第二个 LLM 来模拟用户。我们在 [alignment auditing agents](https://alignment.anthropic.com/2025/automated-auditing/) 中使用这种方法，通过延长的对抗性对话对模型做压力测试。

对话智能体的成功可以是多维的：工单是否已解决（状态检查）、是否在 <10 轮内完成（transcript 约束），以及语气是否适当（LLM 量规）？两个纳入多维性的基准是 [𝜏-Bench](https://arxiv.org/abs/2406.12045) 及其后继者 [τ2-Bench](https://arxiv.org/abs/2506.07982)。它们模拟跨零售支持和航空预订等领域的多轮交互，其中一个模型扮演用户角色，而智能体导航现实场景。

**示例：对话智能体的理论评估**

考虑一项支持任务，智能体必须为一位沮丧的客户处理退款。

```plaintext
graders:
  - type: llm_rubric
    rubric: prompts/support_quality.md
    assertions:
      - "Agent showed empathy for customer's frustration"
      - "Resolution was clearly explained"
      - "Agent's response grounded in fetch_policy tool results"
  - type: state_check
    expect:
      tickets: {status: resolved}
      refunds: {status: processed}
  - type: tool_calls
    required:
      - {tool: verify_identity}
      - {tool: process_refund, params: {amount: "<=100"}}
      - {tool: send_confirmation}
  - type: transcript
    max_turns: 10
tracked_metrics:
  - type: transcript
    metrics:
      - n_turns
      - n_toolcalls
      - n_total_tokens
  - type: latency
    metrics:
      - time_to_first_token
      - output_tokens_per_sec
      - time_to_last_token
```

与我们的编程智能体示例一样，这项任务为说明目的展示了多种评分器类型。在实践中，对话智能体评估通常使用基于模型的评分器来同时评估沟通质量和目标完成，因为许多任务——例如回答一个问题——可能有多个“正确”方案。

### 评估研究智能体

**研究智能体（Research agents）** 收集、综合和分析信息，然后产出答案或报告等输出。与单元测试提供二元通过/失败信号的编程智能体不同，研究质量只能相对于任务来判断。什么算作“全面”、“来源可靠”，甚至“正确”，取决于 context：市场扫描、收购尽职调查和科学报告各自需要不同标准。

研究评估面临独特挑战：专家可能对一份综合是否全面意见不一，随着参考内容不断变化，ground truth 会移动，而更长、更开放的输出为错误创造了更多空间。例如，像 [BrowseComp](http://arxiv.org/abs/2504.12516) 这样的基准测试 AI 智能体是否能在开放网络中大海捞针——这些问题被设计为易于验证但难以解决。

构建研究智能体评估的一种策略是组合评分器类型。Groundedness 检查验证主张是否由检索到来源支持，覆盖检查定义一份好答案必须包含的关键事实，来源质量检查确认所咨询的来源是权威的，而不仅仅是最先检索到的。对于有客观正确答案的任务（“公司 X 的 Q3 收入是多少？”），精确匹配有效。LLM 可以标记没有支持的主张和覆盖缺口，也可以验证开放式综合的连贯性和完整性。

鉴于研究质量的主观性质，基于 LLM 的量规应当经常对照专家人类判断进行校准，以便有效为这些智能体打分。

### 计算机使用智能体

**计算机使用智能体（Computer use agents）** 通过与人类相同的界面与软件交互——截图、鼠标点击、键盘输入和滚动——而不是通过 API 或代码执行。它们可以使用任何带有图形用户界面（GUI）的应用，从设计工具到遗留企业软件。评估需要在真实或沙箱环境中运行智能体，使它可以使用软件应用，并检查它是否达成了预期结果。例如，[WebArena](https://arxiv.org/abs/2307.13854) 测试基于浏览器的任务，使用 URL 和页面状态检查来验证智能体是否正确导航，并对修改数据的任务做后端状态验证（确认订单确实已下，而不仅仅是确认页面出现了）。[OSWorld](https://os-world.github.io/) 把这一点扩展到完整操作系统控制，用评估脚本在任务完成后检查多样产物：文件系统状态、应用配置、数据库内容和 UI 元素属性。

浏览器使用智能体需要在 token 效率和延迟之间取得平衡。基于 DOM 的交互执行很快，但消耗许多 tokens；基于截图的交互更慢，但对 token 更高效。例如，当请 Claude 总结 Wikipedia 时，从 DOM 提取文本更高效。当在 Amazon 上寻找一个新的笔记本保护壳时，截图更高效（因为提取整个 DOM 对 token 很密集）。在我们的 Claude for Chrome 产品中，我们开发了 evals 来检查智能体是否为每个 context 选择了正确的工具。这使我们能更快、更准确地完成基于浏览器的任务。

### 如何思考智能体评估中的非确定性

无论智能体类型如何，智能体行为在不同运行之间都会变化，这使得评估结果比乍看起来更难解释。每项任务都有自己的成功率——也许一项任务 90%，另一项 50%——一次 eval 运行中通过的任务，下一次可能失败。有时，我们想衡量的是智能体对一项任务*多经常*（trials 中的多大比例）成功。

两项指标帮助捕捉这一细微差别：

[**pass@k**](https://proceedings.neurips.cc/paper/2019/file/7298332f04ac004a0ca44cc69ecf6f6b-Paper.pdf) 衡量智能体在 *k* 次尝试中至少得到一个正确方案的可能性。随着 *k* 增加，pass@k 分数上升：更多“射门机会”意味着至少 1 次成功的几率更高。50% 的 pass@1 分数意味着模型在第一次尝试时就成功完成评估中一半的任务。在编程中，我们常常最关心智能体在第一次尝试中找到方案——pass@1。在其他情形中，提出许多方案是有效的，只要其中一个有效。

[**pass^k**](https://arxiv.org/abs/2406.12045) 衡量 *全部 k* 次 trials 都成功的概率。随着 *k* 增加，pass^k 下降，因为要求跨更多 trials 的一致性是一道更难越过的门槛。如果你的智能体每次 trial 成功率为 75%，并且你运行 3 次 trials，三次全部通过的概率是 (0.75)³ ≈ 42%。这一指标对面向客户的智能体尤其重要，因为用户期望每次都有可靠行为。

（原文配图：随着 trials 增加，pass@k 和 pass^k 分叉。在 k=1 时它们相同（都等于每次 trial 的成功率）。到 k=10 时，它们讲述相反的故事：pass@k 接近 100%，而 pass^k 降到 0%。）

两项指标都有用，使用哪一项取决于产品要求：对于一次成功就重要的工具用 pass@k，对于一致性至关重要的智能体用 pass^k。

## 从零到一：通往出色智能体评估的路线图

这一节列出我们关于从没有 evals 走到你可以信任的 evals 的实践、经过现场检验的建议。把它视为评估驱动的智能体开发路线图：尽早定义成功，清晰衡量它，并持续迭代。

### 为初始评估数据集收集任务

**步骤 0. 尽早开始**

我们看到团队推迟构建 evals，因为他们认为需要数百项任务。实际上，从真实失败中抽取的 20–50 项简单任务就是很好的开始。毕竟，在智能体开发早期，对系统的每一次改动往往有清晰、可注意到的影响，而这种大效应量意味着小样本量就足够。更成熟的智能体可能需要更大、更难的 evals 来检测更小的效应，但一开始最好采取 80/20 方法。你等得越久，evals 就越难构建。早期，产品需求自然转化为测试用例。等太久，你就是在从实时系统反向工程成功标准。

**步骤 1. 从你已经手动测试的内容开始**

从你在开发期间运行的手动检查开始——你在每次发布前验证的行为，以及最终用户尝试的常见任务。如果你已经在生产中，查看你的 bug 跟踪器和支持队列。把用户报告的失败转换成测试用例，确保你的 suite 反映实际使用；按用户影响优先排序，帮助你把投入放在真正重要的地方。

**步骤 2：撰写无歧义的、带有参考方案的任务**

把任务质量做对比看起来更难。一项好任务是两位领域专家会独立达成相同通过/失败裁决的任务。他们自己能通过该任务吗？如果不能，任务需要精炼。任务规格中的歧义会变成指标中的噪声。这对基于模型的评分器的标准同样适用：模糊的量规产生不一致的判断。

每项任务都应当能被正确遵循指令的智能体通过。这可能很微妙。例如，审计 Terminal-Bench 揭示：如果一项任务请智能体写脚本但没有指定文件路径，而测试假定脚本有特定文件路径，智能体可能并非因其自身过错而失败。评分器检查的一切都应当从任务描述中清晰可见；智能体不应当因模糊规格而失败。对于前沿模型，跨许多 trials 的 0% 通过率（即 0% pass@100）最常常是任务损坏的信号，而不是智能体无能的信号，也是仔细复查任务规格和评分器的信号。对每项任务，创建一份参考方案是有用的：一份通过全部评分器的已知可用输出。这证明任务是可解的，并验证评分器配置正确。

**步骤 3：构建平衡的问题集**

既测试行为*应当*发生的情形，也测试它*不应当*发生的情形。单边评估造成单边优化。例如，如果你只测试智能体在应当搜索时是否搜索，你最终可能得到一个几乎对一切都搜索的智能体。尽量避免[类别不平衡](https://developers.google.com/machine-learning/crash-course/overfitting/imbalanced-datasets)的评估。我们在为 [Claude.ai](http://claude.ai) 中的网页搜索构建 evals 时亲身体会到这一点。挑战是防止模型在不应当搜索时搜索，同时保留它在适当时做广泛研究的能力。团队构建了覆盖两个方向的评估：模型应当搜索的查询（例如查找天气），以及它应当凭已有知识作答的查询（例如 “who founded Apple?”）。在触发不足（应当搜索时不搜索）和触发过度（不应当搜索时搜索）之间取得正确平衡是困难的，并对 prompts 和评估都进行了许多轮精炼。随着更多示例问题出现，我们继续向评估添加内容以改进覆盖。

### 设计评估 harness 和评分器

**步骤 4：构建带有稳定环境的稳健评估 harness**

至关重要的是，评估中的智能体功能与生产中使用的智能体大致相同，并且环境本身不引入进一步噪声。每一次 trial 都应当通过从干净环境开始而“隔离”。运行之间不必要的共享状态（残留文件、缓存数据、资源耗尽）可能因基础设施不稳定而不是智能体表现造成相关失败。共享状态也可能人为抬高表现。例如，在一些内部评估中，我们观察到 Claude 通过检查先前 trials 的 git 历史，在某些任务上获得了不公平优势。如果多个不同 trials 因环境中的同一限制（例如有限的 CPU 内存）而失败，这些 trials 就不是独立的，因为它们受同一因素影响，评估结果对于衡量智能体表现就变得不可靠。

**步骤 5：深思熟虑地设计评分器**

如上所述，出色的评估设计涉及为智能体和任务选择最佳评分器。我们建议在可能的地方选择确定性评分器，在必要或需要额外灵活性的地方使用 LLM 评分器，并审慎使用人工评分器做额外验证。

有一种常见本能是检查智能体是否遵循了非常特定的步骤，例如按正确顺序的一系列工具调用。我们发现这种方法过于僵硬，并导致过于脆弱的测试，因为智能体经常找到评估设计者没有预料到的有效方法。为了不必要地惩罚创造性，通常更好的是为智能体产出了什么打分，而不是它走的路径。

对于有多个组成部分的任务，内置部分学分。一个正确识别问题并验证客户、但未能处理退款的支持智能体，明显好于立即失败的智能体。在结果中表示这一成功连续体很重要。

模型评分常常需要仔细迭代来验证准确性。LLM-as-judge 评分器应当与人类专家密切校准，以获得人类评分与模型评分之间分歧很小的信心。为避免幻觉，给 LLM 一条出路，例如提供一条指令，在它没有足够信息时返回 “Unknown”。为任务的每个维度创建清晰、结构化的量规，然后用隔离的 LLM-as-judge 为每个维度打分，而不是用一个为所有维度打分，也会有帮助。一旦系统稳健，偶尔使用人工审阅就足够了。

有些评估有微妙的失败模式，即使智能体表现良好也会导致低分，因为智能体因评分 bug、agent harness 约束或歧义而未能解决问题。即使是经验丰富的团队也可能错过这些问题。例如，[Opus 4.5 最初在 CORE-Bench 上得到 42%](https://x.com/sayashk/status/1996334941832089732?s=46&t=c5pEvnVdVbMkcR_rcCHplg)，直到一位 Anthropic 研究员发现了多个问题：僵硬的评分在期望 “96.124991…” 时惩罚 “96.12”、模糊的任务规格，以及不可能精确复现的随机任务。在修复 bug 并使用约束较少的 scaffold 之后，Opus 4.5 的分数跃升到 95%。类似地，[METR 发现](https://x.com/metr_evals/status/2001473506442375645?s=46) 他们时间跨度基准中的若干配置错误的任务，要求智能体优化到一个声明的分数阈值，但评分要求超过该阈值。这惩罚了像 Claude 这样遵循指令的模型，而忽略所声明目标的模型得到了更好分数。仔细复查任务和评分器可以帮助避免这些问题。

使你的评分器对绕过或黑客行为有抵抗力。智能体不应当能轻易“作弊”评估。任务和评分器应当被设计为：通过真正要求解决问题，而不是利用意外漏洞。

### 长期维护并使用评估

**步骤 6：检查 transcripts**

除非你阅读许多 trials 的 transcripts 和评分，否则你不会知道评分器是否工作良好。在 Anthropic，我们投资了查看评估 transcripts 的工具，并定期花时间阅读它们。当一项任务失败时，transcript 告诉你智能体是犯了真正的错误，还是你的评分器拒绝了一个有效方案。它也常常揭示关于智能体和评估行为的关键细节。

失败应当看起来公平：清楚智能体哪里错了以及为什么。当分数不上升时，我们需要有信心这是由于智能体表现而不是评估。阅读 transcripts 是你验证评估正在衡量真正重要的事情的方式，也是智能体开发的一项关键技能。

**步骤 7：监控能力评估饱和**

100% 的评估跟踪退化，但不提供改进信号。**评估饱和（Eval saturation）** 发生在智能体通过了全部可解任务、没有留下改进空间时。例如，SWE-Bench Verified 分数今年从 30% 开始，前沿模型现在正接近 >80% 的饱和。随着评估接近饱和，进展也会放缓，因为只剩下最难的任务。这可能使结果具有欺骗性，因为大的能力改进表现为分数的小幅增加。例如，代码审阅创业公司 [Qodo](https://www.qodo.ai/) 最初对 Opus 4.5 印象不深，因为他们的一次性编程评估没有捕捉到在更长、更复杂任务上的收益。作为回应，他们开发了一套新的智能体式评估框架，提供了关于进展的清晰得多的图景。

作为规则，在有人深入评估细节并阅读一些 transcripts 之前，我们不会把评估分数当作表面价值。如果评分不公平、任务模糊、有效方案被惩罚，或 harness 约束了模型，就应当修订评估。

**步骤 8：通过开放贡献和维护长期保持评估套件健康**

一套评估 suite 是需要持续关注和清晰所有权才能保持有用的活产物。

在 Anthropic，我们实验了各种评估维护方法。被证明最有效的是：建立专门的评估团队来拥有核心基础设施，而领域专家和产品团队贡献大多数评估任务并自己运行评估。

对于 AI 产品团队，拥有并迭代评估应当像维护单元测试一样常规。团队可能在早期测试中“有效”的 AI 功能上浪费数周，却未能满足一套设计良好的评估本会尽早揭示的未声明期望。定义评估任务是压力测试产品需求是否具体到足以开始构建的最佳方式之一。

我们建议实践评估驱动开发：在智能体能够实现计划能力之前构建评估来定义它们，然后迭代直到智能体表现良好。在内部，我们常常构建今天“足够好”的功能，但它们是对模型在几个月内能做什么的押注。从低通过率开始的能力评估使这一点可见。当一个新模型落地时，运行该 suite 会迅速揭示哪些押注得到了回报。

最接近产品需求和用户的人，处于定义成功的最佳位置。凭借当前模型能力，产品经理、客户成功经理或销售人员可以使用 Claude Code 把一项评估任务作为 PR 贡献出来——让他们这样做！或者，更好的是，主动使他们能够这样做。

## 评估如何与其他方法配合，以全面理解智能体

自动化评估可以对照智能体在数千项任务上运行，而无需部署到生产或影响真实用户。但这只是理解智能体表现的许多方式之一。完整图景包括生产监控、用户反馈、A/B 测试、手动 transcript 审阅，以及系统性人工评估。

## 理解 AI 智能体表现的方法概述

| 方法 | 优点 | 缺点 |
| --- | --- | --- |
| **自动化评估**<br>*在没有真实用户的情况下以程序方式运行测试* | • 更快迭代<br>• 完全可复现<br>• 无用户影响<br>• 可以在每次 commit 上运行<br>• 无需生产部署即可在规模上测试场景 | • 需要更多前期投入来构建<br>• 需要随着产品和模型演化持续维护以避免漂移<br>• 如果与真实使用模式不匹配，可能造成虚假信心 |
| **生产监控**<br>*跟踪实时系统中的指标和错误* | • 在规模上揭示真实用户行为<br>• 抓住合成评估错过的问题<br>• 提供智能体实际表现的 ground truth | • 被动；问题在你知道之前就到达用户<br>• 信号可能嘈杂<br>• 需要在仪器化上投入<br>• 缺乏用于评分的 ground truth |
| **A/B 测试**<br>*用真实用户流量比较变体* | • 衡量实际用户结果（留存、任务完成）<br>• 控制混杂因素<br>• 可扩展且系统化 | • 缓慢；需要数天或数周才能达到显著性，并需要足够流量<br>• 只测试你部署的改动<br>• 在无法彻底审阅 transcripts 的情况下，对指标变化背后的“为什么”信号较少 |
| **用户反馈**<br>*如踩或 bug 报告等显式信号* | • 揭示你没有预料到的问题<br>• 带来来自真实人类用户的真实例子<br>• 反馈常常与产品目标相关 | • 稀疏且自我选择<br>• 偏向严重问题<br>• 用户很少解释某件事*为何*失败<br>• 不是自动化的<br>• 主要依赖用户发现问题可能对用户有负面影响 |
| **手动 transcript 审阅**<br>*人类阅读智能体对话* | • 建立对失败模式的直觉<br>• 抓住自动化检查错过的微妙质量问题<br>• 帮助校准“好”看起来像什么并把握细节 | • 耗时<br>• 无法扩展<br>• 覆盖不一致<br>• 审阅者疲劳或不同审阅者可能影响信号质量<br>• 通常只给出定性信号，而不是清晰的定量评分 |
| **系统性人工研究**<br>*由受过训练的评分者为智能体输出做结构化评分* | • 来自多位人类评分者的黄金标准质量判断<br>• 处理主观或模糊任务<br>• 为改进基于模型的评分器提供信号 | • 相对昂贵，周转缓慢<br>• 难以频繁运行<br>• 评分者间分歧需要调和<br>• 复杂领域（法律、金融、医疗）需要人类专家进行研究 |

这些方法映射到智能体开发的不同阶段。自动化评估在上线前和 CI/CD 中尤其有用，在每次智能体改动和模型升级上运行，作为对抗质量问题的第一道防线。生产监控在上线后启动，以检测分布漂移和未预料到的现实世界失败。一旦你有足够流量，A/B 测试验证重大改动。用户反馈和 transcript 审阅是填补缺口的持续实践：持续分诊反馈，每周抽样阅读 transcripts，并在需要时更深入挖掘。把系统性人工研究留给校准 LLM 评分器，或评估主观输出，在这些地方人类共识作为参考标准。

（原文配图：像安全工程中的 [瑞士奶酪模型](https://en.wikipedia.org/wiki/Swiss_cheese_model) 一样，没有任何单一评估层能抓住每一个问题。当多种方法组合时，从一层溜走的失败会被另一层抓住。）

最有效的团队组合这些方法：自动化评估用于快速迭代，生产监控用于 ground truth，定期人工审阅用于校准。

## 结论

没有 evals 的团队会陷入被动循环——修复一次失败、造成另一次，无法区分真实退化与噪声。尽早投入的团队发现相反情况：随着失败变成测试用例、测试用例防止退化、指标取代猜测，开发会加速。Evals 给整个团队一座清晰的可以攀登的山，把“智能体感觉更差了”变成可以采取行动的事情。价值会复合，但只有当你把 evals 当作核心组成部分而不是事后想法时才如此。

模式因智能体类型而异，但这里描述的基本面是恒定的。尽早开始，不要等待完美的 suite。从你看到的失败中获取现实任务。定义无歧义、稳健的成功标准。深思熟虑地设计评分器并组合多种类型。确保问题对模型足够难。迭代评估以改进其信噪比。阅读 transcripts！

AI 智能体评估仍是一个新兴、快速演化的领域。随着智能体承担更长任务、在多智能体系统中协作，并处理日益主观的工作，我们将需要调整我们的技术。我们会在学到更多时继续分享最佳实践。

## 附录：评估框架

若干开源和商业框架可以帮助团队实现智能体评估，而无需从头构建基础设施。正确选择取决于你的智能体类型、现有技术栈，以及你是否需要离线评估、生产可观测性，或两者都需要。

[Harbor](https://harborframework.com/) 被设计用于在容器化环境中运行智能体，带有跨云提供商大规模运行 trials 的基础设施，以及定义任务和评分器的标准化格式。像 Terminal-Bench 2.0 这样的流行基准通过 Harbor registry 发布，使运行既定基准以及定制评估 suites 变得容易。

[Braintrust](https://www.braintrust.dev/) 是一个把离线评估与生产可观测性和实验跟踪结合在一起的平台——对既需要在开发期间迭代、又需要在生产中监控质量的团队很有用。其 `autoevals` 库包含针对事实性、相关性和其他常见维度的预构建评分器。

[LangSmith](https://docs.langchain.com/langsmith/evaluation) 提供 tracing、离线和在线评估，以及与 LangChain 生态紧密集成的数据集管理。[Langfuse](https://langfuse.com/) 作为自托管开源替代方案，为有数据驻留要求的团队提供类似能力。

[Arize](https://arize.com/) 提供 Phoenix，一个用于 LLM tracing、调试以及离线或在线评估的开源平台，以及 AX，一个把 Phoenix 扩展到规模、优化和监控的 SaaS 产品。

许多团队组合多种工具、自己滚动评估框架，或只是用简单评估脚本作为起点。我们发现，虽然框架可以是加速进展和标准化的有价值方式，它们只与你通过它们运行的评估任务一样好。通常最好迅速挑选一套适合你工作流的框架，然后把精力投入评估本身，通过迭代高质量测试用例和评分器来实现。
